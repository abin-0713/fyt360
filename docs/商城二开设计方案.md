# 商城二开设计方案（fyt360-shop）

> 基于上游 [516600864/fyt360](https://github.com/516600864/fyt360) 的第二开发，分支 `shop`。
> 上游升级走 `upgrade.sh`（`REPO_URL` 指向本 fork），本目录所有改动都在上游快照之上叠加。

## 一、设计决策（开工即锁定，避免返工）

| 决策 | 选择 | 理由 |
|---|---|---|
| 商品主表 | **复用 `self_goods`，只加列** | 该表已被 `trade.ts` / `admin-goods.ts` 使用，另建 spu 表会造成两套商品真相源 |
| SKU | **新建 `shop_sku`，从 `self_goods.skus` JSON 迁入** | JSONB 全量覆盖无法做并发安全扣减（必超卖）；`raw` 列保留原始元素，迁移零信息丢失 |
| 商品形态 | `delivery_type` 扩展为 `express \| group \| virtual` | 一套语义覆盖实物快递/到店核销/虚拟卡券，不引入第二组字段 |
| 订单行 | **新建 `shop_order_item`，仅 `provider='self'` 写入** | CPS/直充订单保持"一单一行"，不污染 `ordersync` 的归因逻辑 |
| 金额精度 | 行金额/实付 `NUMERIC(12,2)`；**单价/单件成本 `NUMERIC(12,4)`** | 实测存量数据有 `cost=0.005`（半分钱）的规格，用 2 位会被静默四舍五入，等于改了商家的成本账 |
| 库存语义 | 下单**占用** `locked_stock`，支付后 `stock` 转扣，取消/超时释放 | 与既有 `ordersweep`（关单+回退券+回补库存）语义一致；可售 = `stock - locked_stock` |
| 库存流水 | `shop_stock_log` 只增不改 | 超卖/对账争议时唯一的取证手段 |
| 多商户 | **暂不做**，但支付表已有 `site_id` 维度；分账将来落在 `site_payment` 之上 | 多商户分账要重做支付与结算层，工作量大且需要服务商资质 |
| 迁移编号 | **从 `100_` 起（三位数）** | 上游已用到 `042` 且 `041` 空着可能被补，`100+` 排序在后且永不撞号 |

## 二、本阶段（阶段 1：数据层）交付物

- `deploy/migrations/100_shop_core.sql` —— 7 张新表 + `self_goods` 扩列 + 两处存量回填，**全部幂等**
- `deploy/scripts/verify-shop-migration.mjs` —— 本地嵌入式 PG 验收（20 项断言）
- `npm run verify:shop` —— 一键跑

### 新表

| 表 | 用途 | 关键约束 |
|---|---|---|
| `shop_category` | 商品分类（多级，站点隔离） | `(site_id, COALESCE(parent_id,0), name)` 唯一 |
| `shop_sku` | SKU（价格/成本/库存/销量） | `stock >= 0`、`locked_stock >= 0`、`(site_id,goods_id,sku_code)` 唯一 |
| `shop_cart` | 购物车 | `(user_id, sku_id)` 唯一；`num ∈ [1,999]` |
| `shop_order_item` | 订单行快照 | `refunded_num <= num`、`refund_amount <= amount` |
| `shop_freight_template` | 运费模板（按件/按重、满额包邮） | `charge_mode ∈ (qty,weight)` |
| `shop_refund` | 售后/退款单 | 状态机 `applied→approved→refunding→success/failed`；`wx_refund_id` 回填 |
| `shop_stock_log` | 库存流水 | `reason ∈ (order_create,order_pay,order_cancel,refund,admin_adjust)` |

### 存量回填（幂等）

1. `self_goods.skus[]` → `shop_sku`：`price`/`stock`/`cost`（`cost` 缺失回落商品级 `cost_price`，再缺为 NULL，**不写 0**）
2. `order(provider='self').goods_snapshot` → `shop_order_item`：金额与成本按**下单快照**落库，禁止 JOIN 商品表回算
3. `self_goods.shop_status` 对齐旧 `status`（存量已上架商品不能显示成草稿，否则 C 端"整店消失"）

### 库存与幂等（钱路径的核心约定）

- 可售 = `stock - locked_stock`；下单占用、支付转扣、取消释放
- 幂等键 = `shop_stock_log.ref`（`create:` / `pay:` / `cancel:<order_sn>`）→ 微信回调重试、定时任务重复跑都不会二次扣减
- 两道防超卖闸：① `SELECT … FOR UPDATE` 锁 SKU 行；② 条件 `UPDATE … WHERE stock - locked_stock >= num`
- 关单权仍在上游（`ordersweep`/cancel）；商城只做"已关单但占用未释放"的兜底扫描

### 验收结果（`npm run verify:shop-chain`，40+ 断言）

覆盖：目录/购物车/混类拒单/试算零副作用/下单/并发抢最后 1 件（5 请求仅 1 成功）/支付扣减/回调幂等/虚拟卡券即交付/取消释放/兜底释放/订单列表详情 —— **全部通过**。

### 测试抓到的两个真 bug（都已修）

1. **NaN 订单风险（严重）**：pg 对 `BIGINT/NUMERIC` 返回**字符串**，而代码用数字 key 查 SKU 数量 → 数量 `undefined` → 金额算出 `NaN`；
   偏偏 **PostgreSQL 的 `numeric` 接受 `NaN` 字面量**，会静默落一张金额为 NaN 的订单。
   修法：读库后统一 `Number()` 归一化 + 金额有限性兜底（非有限数当场 500，绝不入库）。
2. 订单行 `num` 因同一原因插空，被非空约束拦下（约束救了这一单）。

### 部署新增任务

商城库存兜底释放需在宝塔计划任务里加第 4 条（每 5 分钟）：
`APP_DIR=/www/wwwroot/fyt360-src /root/fyt360-bt/jobs.sh shop-sweep`
（`jobs.sh` 无需改动，任意任务名都支持；token 由 `HMAC(JWT_SECRET,'shop-sweep')` 现算）

## 八、阶段 4（退款与售后）已交付 —— 2026-10-07

### 新增文件

| 文件 | 作用 |
|---|---|
| `server/src/lib/shop-refund.ts` | 售后申请 / 审核 / 微信 V3 退款 / 落账（库存回补+返利冲销）/ 确认收货结算 |
| `deploy/scripts/verify-shop-refund.mjs` | 对账级验收（52 项），`npm run verify:shop-refund` |

C 端新增：`POST /orders/:id/receive`、`POST /orders/:id/refund`、`GET /refunds[/:id]`、`POST /refunds/:id/cancel`
后台新增：`GET /refunds[/:id]`、`POST /refunds/:id/approve|reject|finish`、`POST /orders/:id/settle`

### 三个关键业务决策

1. **快递单必须补「确认收货」才能结算返利**
   上游的返利（元宝 + 佣金）由 `settleRebateOnVerify()` 在**核销时**发放 —— 但快递单没有核销动作，
   照搬上游会导致**快递单佣金永远不发**。商城补了 `receive` 接口触发结算（幂等，重复点不重复发）。
   到店核销单仍走上游核销流程，线上确认收货被明确拒绝（`GROUP_ORDER`）。

2. **微信退款直接复用上游已实现的 `refund()`**（V3 `out_refund_no = refund_sn`，微信侧天然幂等）；
   未配置真实商户号时走 **mock 通道**自动落账（与上游 `mock-pay` 同款安全边界：配了真凭据即自动失效），
   这样在拿到商户号之前就能把售后流程跑通。

3. **部分退款的佣金不自动冲销**
   多跳佣金按 `level` 各一行，按比例扣会污染历史账；部分退款只在
   `shop_refund.reversed` 台账里标 `manual_review` 交运营人工处理 —— **宁可要人确认，也不要静默算错**。
   全额退款才自动作废佣金并扣回余额。

### 冲销的资金语义（严格对齐上游设计意图）

| 动作 | 落点 |
|---|---|
| 库存回补 | `shop_sku.stock += num` + `shop_stock_log(reason='refund', ref='refund:<refund_sn>')` |
| 元宝扣回 | `ingot_tx(type='REFUND_DEDUCT', amount=-N)`（幂等唯一索引 `uq_ingot_tx_order_ref`）；余额不足的部分进 `ingot_account.frozen` **挂账**（上游注释即此设计） |
| 佣金作废 | `commission_flow.status='invalid'` + `promoter.commission_balance` 扣回（CHECK >= 0，扣不动的差额记 shortfall） |
| 审计 | 全部明细写进 `shop_refund.reversed` JSONB |

### 验收结果（52 项断言，全部通过）

- 确认收货 → `paid` → `settled`、元宝 20000 到账、L3 自购佣金 24 元入推广余额；重复收货不重复发
- 全额退款 → 库存 8→10、订单行退款量、订单 `refunded`、元宝 −20000、佣金 `invalid`、推广余额扣回 0
- **幂等**：重复审核返回 `already`，库存不再变、元宝流水仍 1 条、退款量不翻倍
- 未结算单部分退款 → 台账记"无返利可冲销"；已结算单部分退款 → 台账记 `manual_review` 且佣金保持 `available`
- 状态守卫：未支付不可申请售后/不可收货、未发货不可收货、核销单不可线上收货、超量退款 409、驳回必须填原因
- 后台售后列表/详情（含冲销台账）与"强制结算"兜底可用

### 本轮修的两个真问题

1. **结算失败会阻断确认收货**：`settleRebateOnVerify` 抛错（实测是 `promoter.invite_code` 非空约束）
   会让买家卡在"收了货但订单没完成"。已改为 try/catch 隔离 + 留痕，运营可用 `/orders/:id/settle` 补结算。
2. **只传 `num` 不传 `item_id` 的歧义请求**：原实现会走整单退款分支**静默忽略 `num`** ——
   调用方以为"只退 1 件"，实际退了整单。已改为显式 400 `ITEM_ID_REQUIRED`。

### 顺手修掉的上游真 bug（H5 老用户白屏）

`apps/h5/src/core/bootstrap.js` 里 `const invite = qs.get('invite')` 声明在「已有 token」分支**之后**，
而该分支内先用了 `invite` → **老用户（localStorage 已有 token）每次进站都命中 TDZ**，
抛 `Cannot access 'invite' before initialization`（压缩后变量名 `o`）。

- 复现证据：未改动的上游产物 + 注入 token → 同样报错；无 token → 0 报错
- 影响：返回用户的 H5 首页 `ensureBoot()` 抛错，站点配置/首页 Schema 拉取被中断
- 修法：把 `const invite` 提前到函数开头（1 行位置调整），并把说明写进注释
